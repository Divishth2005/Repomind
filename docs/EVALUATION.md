# Module 6 — Multi-Repository Evaluation

Goal (build plan Sec 31, 40): check whether the pipeline and the Module 4/5
metrics behave sensibly beyond one repository, and find where they break.

All numbers are in [EVALUATION_RESULTS.md](EVALUATION_RESULTS.md)
(generated by `python -m evaluation.cli`). This file is the interpretation.

Reproduce:

```bash
python -m evaluation.acquire   # runs the pipeline for each repo (~35 min, resumable)
python -m evaluation.cli       # computes statistics + experiments, writes the tables
```

## Set

8 public, non-fork repositories, 198 to 7,713 commits, 4 languages (Python,
Rust, JavaScript, Go): flask, requests, fastapi, ripgrep, black, express,
cobra, ora. The plan suggests 10–20; 8 is a first validation sample. The set
was chosen for variety, using my prior expectations of each project's
contributor structure, so it is not a random sample and "consistent with
expectations" below is weak evidence, not validation.

## Findings

**1. The pipeline generalizes.** All 8 repositories ran end to end with no
failures and no structural validation issues (no dangling references).
Caveat: validation is structural only; correctness of the relationships was
spot-checked by hand on flask (top contributors match its known
maintainers) but a systematic manual sample (plan Sec 40.2) has not been done.

**2. Git↔GitHub identity linkage is weak everywhere.** Only 1–25% of human
commits sit under an identity linked to a GitHub login (via GitHub's noreply
commit email), and only 0–5 of each repo's top-10 committers are linked.
So for most people, commit activity and PR/review/issue activity are
attached to different identities. This is the flask `David Lord` /
`davidism` problem from Module 4 seen in every repo, and it is the biggest
weakness for any signal that mixes Git and GitHub data (metric E, reviewer
diversity). Bots are 0–44% of commits (fastapi 44%) and are flagged.

**3. PR→file linkage depends on merge style, and is 0% for three repos.**
Share of PRs whose commits appear in history: flask 48%, requests 45%,
express 10%, cobra 10%, ripgrep 5%, and **0% for fastapi, black and ora**
(so 6,359 + 2,469 + 100 PRs and about 12,700 reviews contribute nothing to
file-level signals there). The likely cause is squash merging: those repos
have no merge commits, and 46% (fastapi) and 79% (black) of commit subjects
end in `(#PR-number)`, GitHub's squash-merge default. That number would
allow the link to be recovered without re-downloading anything. The cause is
inferred from this evidence, not confirmed, and the fix is not implemented.

**4. Concentration behaves differently across repos, in the expected
direction.** Median effective contributors per file ranges from 1.4
(ripgrep) to 5.0 (black, cobra); the share of files where one person made
>= 80% of commits ranges from 2% (cobra) to 58% (ripgrep). ripgrep and express
are the most concentrated, black and cobra the most distributed. The
multi-signal metric E correlates 0.85–0.94 with the plain commit-based
metric in every repo, but that is largely by construction: with PR/review
signals missing (finding 3), E is built almost entirely from commit-derived
signals. So E's agreement with A is not evidence that E is better or worse.

**5. Recency half-life is the most influential setting; bots and same-name
identity merging barely matter.**

| Change | Rank correlation of file-level concentration | Notes |
|---|---|---|
| half-life 90d vs 365d | 0.56–0.92 (7 repos with >= 88 ranked files); lowest cobra 0.56, requests 0.61 | ora 0.28 but only 9 ranked files |
| half-life 365d vs 1095d | 0.69–0.97 | |
| bots included vs excluded | 0.96–1.00 | fastapi: top committer changes for 14 of 1,697 files; black 16 of 214 |
| conservative vs same-name-merged identities | 0.98–1.00 | merges away 16–136 identities (0 in ora) |

The identity result is limited: the alternative only merges identities with
the same display name, so it does not test cross-source linking (finding 2)
or differently-named aliases. Ranking is stable to what was tested, not to
identity resolution in general.

**6. Risk levels are not stable to the "active" window in sparsely active
repos.** Agreement of risk levels between a 365-day and a 180-day window is
high for flask (91%), requests (100%) and ora (100%), but low for ripgrep
(40%), black (50%), express (50%), cobra (50%) and fastapi (13%).
In fastapi 85 of the 114 assessable components turn `dormant` when the window
shrinks, and 14 more change level. At a 730-day window agreement is 50–100%
(lowest cobra 50%, requests 58%). The exact counts of `high` / `medium`
should therefore always be quoted with the window. Also, `low` is rare
(0 in five of the eight repos), which suggests the level cut-offs are
sensitive; that has not been tuned.

## What this does and does not show (research questions)

| RQ | Status |
|---|---|
| RQ1 heterogeneous Git+GitHub data → structured model | Supported: works on 8 repos; linkage gaps quantified (findings 2, 3) |
| RQ2 which signals are useful for concentration | Partly: commit-derived signals are available everywhere; PR/review signals are only usable where merges preserve commits |
| RQ3 effect of identity resolution | Partly: same-name merging changes little; the large unresolved issue is Git↔GitHub linkage, whose effect on the metrics is **not yet measured** |
| RQ4 retrieval improves LLM grounding | Not started (Modules 7–9) |
| RQ5 concentration signals identify maintenance-risk areas | **Not answered.** Nothing here checks whether flagged components actually became maintenance problems. That needs a temporal backtest (compute signals as of an earlier date, see what happened next) |

## Limitations of this evaluation

- 8 repos, mostly popular projects, 4 of 8 in Python; a single run each.
- Default branch only; renames not tracked (the flask `flask/`→`src/flask/`
  rename splits history; it likely affects other repos too, unmeasured).
- No ground truth and no manual correctness sample.
- Sensitivity results describe how much rankings move, not whether either
  ranking is right.

## Suggested next steps (not done)

1. Recover squash-merged PR→commit links from `(#N)` in commit subjects (or
   fetch `mergeCommit` from GitHub) and re-run the evaluation.
2. Improve Git↔GitHub identity linking (e.g. GitHub's per-commit
   `author.user.login`) and measure its effect on metric E and reviewer
   diversity.
3. Temporal backtest for RQ5.
4. Extend to 10–20 repositories, including some outside Python.
